# Tabsurd: сервер синхронизации

Статус: проект, 2026-10-11.
Связанные документы: `docs/specification.md` (идея, части и режимы), `docs/extension/specification.md` (требования расширения, раздел 6), `docs/sync_server/technologies.md` (технологии сервера), `docs/extension/technologies.md` (технологии расширения).

Удалённый сервер на своём VPS. Хранит открытые окна и вкладки, сохранённые окна и группы, недавно закрытые вкладки и снимки окон, чтобы у одного аккаунта они были одинаковыми на всех компьютерах. Не путать с **локальным сервисом** video-analyzer (`video-analyzer/docs/local_service/local_service.md`): тот на компьютере пользователя, и друг с другом они не общаются.

---

## 1. Вход и аккаунты

- Расширение получает токен Google-аккаунта профиля Chrome (`chrome.identity.getAuthToken`).
- Сервер проверяет у Google, что токен выдан именно расширению Tabsurd, и берёт постоянный номер Google-аккаунта. Дальше сервер выдаёт свой токен, чтобы не обращаться к Google на каждый запрос.
- **Только разрешённые аккаунты.** Список разрешённых адресов почты — в настройках сервера; остальным отказ.
- Разовая подготовка: проект в Google Cloud с OAuth client типа «Chrome extension» и постоянный ID расширения (ключ в манифесте).
- Профиль без входа в Chrome синхронизацию не включает и работает только локально.

## 2. Модель данных

| Таблица | Что в ней |
|---|---|
| `accounts` | номер Google-аккаунта, адрес почты |
| `devices` | компьютеры и профили аккаунта: название. Нужны, чтобы снимки окон хранились по компьютерам |
| `records` | все синхронизируемые записи |

Поля `records`:

| Поле | Смысл |
|---|---|
| аккаунт, коллекция | `open_window`, `open_tab`, `saved_group`, `closed_tab`, `window_snapshot` |
| номер записи | UUID, создаёт расширение |
| номер изменения | растёт в пределах аккаунта, выдаёт сервер |
| поля и время изменения каждого поля | для слияния по полям; время — по часам сервера |
| пометка «удалено» | удаление тоже синхронизируется: запись остаётся с датой удаления `deleted_at` по часам сервера («надгробие»). Восстановление из корзины — обычное изменение поля: пометка снимается. Через **90 дней** от записи остаётся только надгробие, через **180** она стирается (раздел 3.1) |

**Слияние по полям.** Для каждого поля побеждает более позднее изменение. **Время изменения — по часам сервера**, а не компьютера: часы компьютеров могут отставать или спешить. Каждый ответ сервера содержит его время; расширение считает поправку «время сервера − время компьютера» (с учётом половины времени запроса) и ставит действию время в момент действия с этой поправкой. Без сети используется последняя известная поправка: часы уходят медленно. Время из будущего сервер заменяет своим текущим. Функция слияния и схемы записей — в `sync-core/`: одну и ту же функцию вызывают сервер (при приёме изменений) и расширение (при получении чужих изменений поверх своих неотправленных). Иначе компьютеры могли бы молча разойтись.

**Сквозное шифрование** не делается, но модель его допускает: значение каждого поля можно будет шифровать отдельно, оставив открытым время изменения, и сервер продолжит сливать по полям, не видя содержимого.

## 3. Протокол

- **Отправка:** `POST /api/v1/sync/push` — пачка изменений. Сервер сливает их с хранимыми и выдаёт номера изменений.
- **Получение:** `GET /api/v1/sync/changes?since=N` — всё, что изменилось после номера N.
- **Когда расширение спрашивает сервер:** при запуске Chrome, при открытии страницы расширения, при пробуждении компьютера из сна и по будильнику раз в 10 минут; отправляет — сразу после изменения, если сервер доступен. Доступность проверяется запросом `GET /api/v1/health`; если он не прошёл, изменения остаются в очереди. Задержка в несколько минут допустима: за двумя компьютерами одновременно работают редко.
- **WebSocket нет.** Если понадобятся мгновенные обновления, его можно добавить: он только сообщал бы «есть изменения до номера N» и вызывал тот же `/api/v1/sync/changes`, протокол бы не менялся.
- **Открытые окна и вкладки** — коллекции `open_window` (постоянный номер окна, место в порядке окон) и `open_tab` (окно, место в окне, адрес, заголовок, группа, закреплена ли). Окно или вкладка, закрытые на одном компьютере, получают пометку «удалено» и закрываются на остальных. Сливаются по тем же правилам, что остальные записи: если два компьютера меняли вкладки без связи, открытое на любом остаётся открытым везде, закрытое на любом закрывается везде, а для каждого поля побеждает последнее изменение. Размер и положение окон на экране не синхронизируются — у компьютеров разные мониторы. Как расширение применяет пришедшие изменения — `docs/extension/specification.md`, раздел 3.3.
- **Снимки окон** уходят на сервер, когда попадают в историю, и хранятся по тем же правилам, что в расширении (`docs/extension/pages/recovery.md`, раздел 1).
- **История поиска** — коллекция `search_query`: текст запроса, время последнего запуска, сколько раз запускали. Одинаковая на всех компьютерах аккаунта. Забытый запрос получает пометку «удалено». Хранится без ограничения числа (`docs/extension/pages/search.md`, раздел 2.1).

**Адреса** — с `/api/v1/`, в стиле REST, как у локального сервиса (`video-analyzer/docs/local_service/local_service.md`, раздел 7). Номер версии нужен потому, что на других компьютерах может долго работать старое расширение: при несовместимом изменении сервер какое-то время отвечает и по `/api/v1/`, и по `/api/v2/`.

**Договор** — свой `openapi.yaml` у сервера синхронизации, отдельно от договора локального сервиса. Если появится WebSocket, его сообщения описываются схемами в этом же файле.

### 3.1. Чистка пометок «удалено»

Решено 2026-10-13.

- **Раз в сутки** по расписанию (`@Cron` в NestJS) сервер проходит по записям с `deleted_at`:
  - **до 90 дней** — запись хранится целиком и восстанавливается снятием пометки. Расширение у себя хранит удалённое 30 дней, а записи 30–90 дней корзина подгружает с сервера (`GET /api/v1/sync/trash`, `docs/extension/pages/trash.md`);
  - **90–180 дней** — **надгробие**: содержимое стирается, остаются только id, пометка и дата (около 100 байт). Восстановить уже нельзя, но отставший клиент ещё узнает об удалении;
  - **старше 180 дней** — запись стирается совсем.
- Компьютеру, который был без связи до полугода, полная синхронизация не нужна.
- Сервер запоминает **границу чистки** — номер изменения, до которого надгробия могли быть стёрты (180 дней).
- **Чистка не синхронизируется:** каждая сторона стирает сама по своему сроку. Стёртая запись больше ни от кого не придёт, потому что у всех она уже помечена.
- **Полная синхронизация.** Если клиент просит `changes?since=N`, а N раньше границы чистки, сервер отвечает «нужна полная синхронизация» вместо изменений. Клиент:
  1. забирает все живые записи заново;
  2. свои записи, которых нет на сервере и которые не менялись после границы, считает удалёнными: их пометку сервер уже стёр;
  3. свои записи, изменённые после границы, отправляет как обычно.

## 4. Отложено

- **Развёртывание на VPS** (Docker, HTTPS, домен, резервные копии) — не планируется, пока не будет готов сам сервер.
