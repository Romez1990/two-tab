## 2. Решения

### 2.1. Сборка — WXT, pnpm

Точки входа задаются файлами: скрипты на сайтах, страницы, фоновый скрипт. WXT сам пишет `manifest.json`, перезагружает расширение при правках и умеет показывать интерфейс на чужой странице в Shadow DOM. Пакеты ставит pnpm: каждый пакет хранится на диске один раз, а в `node_modules` проектов — ссылки на него, поэтому установка быстрее, чем у npm, и антивирусу меньше файлов для проверки. Версия pnpm закреплена полем `packageManager` в `package.json`, запускается через corepack (`corepack enable pnpm`).

### 2.2. Страницы расширения — React

Страницы — это большие списки с фильтрами, сортировкой и графиками. У React для этого больше всего готовых библиотек, и WXT поддерживает его официально.

- Таблицы — TanStack Table, прокрутка десятков тысяч строк — TanStack Virtual.
- Загрузка и кеш данных локального сервиса — TanStack Query.
- Графики — ECharts: тепловая карта «день × час», календарь, масштабирование, большие объёмы данных.
- Компоненты — **MUI (Material UI)**: кнопки, списки, таблицы, диалоги, вкладки, уведомления в стиле Material Design. Самая зрелая библиотека Material Design для React: полный набор компонентов, тема (цвета, светлая и тёмная), значки `@mui/icons-material`. Шрифт Roboto — пакетом `@fontsource/roboto` внутри бандла, не с Google Fonts. Плашки на сайтах — тоже страницы расширения с MUI (раздел 2.4).

### 2.3. Архитектура — Feature-Sliced Design

Код расширения раскладывается по слоям FSD. Слой может импортировать только слои ниже себя, а слайсы одного слоя друг друга не импортируют.

| Слой | Что в нём у Tabsurd |
|---|---|
| `app` | запуск каждой точки входа: провайдеры React, роутер страниц, инициализация Dexie и настроек |
| `pages` | страницы: «Сохранённые», «Окна», «Восстановление», «Топ», «Статистика обо мне», «Итоги», «Настройки», «Первый запуск» |
| `widgets` | крупные блоки страниц: таблица видео, тепловая карта, список окон, очередь скачивания |
| `features` | действия пользователя: сохранить и закрыть группу, вернуть, «Не закрывать», скачать, поставить симпатию, подключиться к Tidy Reel |
| `entities` | сущности: окно, группа, вкладка, снимок, видео, канал, скачивание — модель, хранилище, отображение |
| `shared` | общее без предметной области: клиент API локального сервиса, обёртка над Dexie и `chrome.*`, UI-компоненты, работа со временем (сутки с 6:00) |

Внутри слайса — сегменты `ui`, `model`, `api`, `lib`, наружу он отдаёт только публичный `index.ts`.

Точки входа WXT (`entrypoints/`) остаются тонкими: фоновый скрипт, скрипты на сайтах и страницы только вызывают код из `app`. Фоновый скрипт и плашка без React тоже пользуются слоями `features`, `entities` и `shared`, просто без сегмента `ui` на React.

Правила импорта проверяются автоматически линтером (например, Steiger или правила ESLint для FSD).

### 2.4. Плашки на сайтах — страница расширения в iframe

- **Каждая плашка — страница расширения в `iframe`** (`saved-banner.html`, `download-banner.html`) на React и MUI, как остальные страницы. Сайт не может прочитать её содержимое, его стили на неё не влияют, компоненты и тема — общие со страницами расширения.
- **Плашки не прописаны в манифесте.** Фоновый скрипт внедряет маленький скрипт плашки через `scripting.executeScript` только на ту вкладку и только когда плашка нужна: адрес сохранён, страница видео известного сайта. Скрипт вставляет `iframe` и больше ничего не делает. На остальных сайтах плашек и их скриптов нет вовсе.
- **Две плашки — два отдельных `iframe`**, в разных углах и в разных случаях; вместе они бывают только на сохранённой странице видео. Пока не объединяются.
- **Каждую можно выключить** в настройках (`docs/extension/pages/settings.md`, раздел 6): выключенную фоновый скрипт не внедряет, а уже открытые плашки убирают свой `iframe` сразу на всех вкладках, без перезагрузки (`docs/extension/pages/site_page.md`, раздел 0).
- Тяжёлый для сайтов скрипт — не плашки, а учёт просмотров во всех рамках (раздел 2.7).

### 2.5. Хранилище

- **IndexedDB через Dexie** — сохранённые окна и группы, недавно закрытые вкладки, снимки окон, очередь синхронизации, наблюдения до отправки в локальный сервис. Это основная копия данных профиля.
- **`chrome.storage.sync` и `chrome.storage.local`** — настройки (`docs/extension/specification.md`, раздел 1.2). Изменение сразу видят все части расширения.

Вкладки и страницы расширения одного браузера синхронизируются через это хранилище, без сервера. Скрытая вкладка не перерисовывается; при возврате на неё применяет последнее состояние (раздел 2.6.2).

- **Подписка на изменения базы, без опроса** (решено 2026-10-16). Таблицу меняет только её репозиторий, и он же даёт подписку на её изменения (например, `watchCheckState`). Внутри подписка — живой запрос Dexie (`liveQuery`): он видит запись из любой части расширения (фоновый скрипт, служебная страница, вкладка) и будит подписчиков. Забыть оповещение нельзя: его делает сама база при записи. Опроса «раз в секунду» нет.
- **Таймеры** остаются только там, где по смыслу нужно время: будильник истории снимков и автозакрытия раз в 10 минут, переподключение к локальному сервису. Задержки на 300 мс – 2 с после событий вкладок — не опрос, а склейка серии событий в одно действие.

### 2.6. Связь с серверами

- **Локальный сервис** — WebSocket `ws://127.0.0.1:<порт>/api/ws` для состояния и событий (`docs/extension/queues.md`, раздел 6; `tidy-reel/docs/local_service/local_service.md`, раздел 7.7) и HTTP на `http://127.0.0.1:<порт>/api/…` для действий и разовых проверок — со страниц и из фонового скрипта расширения; скрипт на странице сайта сам в `localhost` не ходит. Договор — копия `api/openapi.yaml` репозитория Tidy Reel в `extension/api/local-service.openapi.yaml`, типы из неё — в `src/shared/api/local-service/schema.d.ts`. Оба файла в git, чтобы расширение собиралось без Tidy Reel рядом.
- **Обновление договора** — `pnpm api:update`: копирует файл из Tidy Reel и заново строит типы. Путь к Tidy Reel — в `extension/.env.local` (не в git): `TIDY_REEL_DIR=…`; без него команда объясняет, что задать.
- **Сервер синхронизации** — HTTP-запросы, без постоянного соединения: при запуске Chrome, при открытии страницы расширения, при пробуждении компьютера из сна и по будильнику раз в 5–10 минут (`docs/sync_server/specification.md`, раздел 3). Будильник — `chrome.alarms`; пробуждение из сна определяется по `chrome.idle` и по пропуску будильника.
- **Service worker спит, когда нечего делать**: его будят события вкладок, кнопок и будильник. В профиле, подключённом к Tidy Reel, его держит открытым WebSocket с локальным сервисом: сервис шлёт `ping` каждые 25 секунд.

### 2.6.1. Состояние серверов

Решено 2026-10-16. Расширение работает с двумя серверами: локальным сервисом Tidy Reel (`local`) и сервером синхронизации (`sync`). Жив ли каждый из них, расширение знает в одном месте, и все его части реагируют одинаково. Логика одна на оба сервера — общий модуль в `shared` с двумя экземплярами; различаются только способ проверки и частота.

- **Одно состояние на сервер.** Его ведёт фоновый скрипт и кладёт в `chrome.storage.session`; читают его через один хук `useServerStatus('local' | 'sync')`, а изменение приходит всем сразу по `storage.onChanged`: страницам, popup, плашкам на сайтах. Значения:
  - `not_connected` — сервер не настроен: профиль не подключён к Tidy Reel или не выполнен вход на сервер синхронизации;
  - `online` — сервер отвечает;
  - `offline` — сервер не отвечает **с самого запуска Chrome**. Это нормально: выключен и выключен. Функции, которым он нужен, недоступны, но тревоги нет;
  - `lost` — сервер был `online` в этом запуске Chrome и **перестал отвечать**: упал или его остановили. Функции недоступны, и пользователю показывается тревога (ниже);
  - `revoked` — сервер отвечает, но нас не принимает: Tidy Reel забыл профиль (его отключили командой меню), вход на сервер синхронизации истёк.
- **«Был `online` в этом запуске»** хранится там же, в `chrome.storage.session`: переживает засыпание фонового скрипта и сбрасывается при перезапуске Chrome.
- **Одна ошибка на оба сервера — `ServerUnreachableError`** с полем `server: 'local' | 'sync'`. Её бросает клиент сервера, когда запрос не дошёл (сервер не запущен, порт закрыт, нет сети). Где бы её ни поймали (форма «Скачать», поиск, пресеты, отправка изменений синхронизации), она сообщает фоновому скрипту, что сервер, похоже, лёг. Тот сразу переводит состояние этого сервера (`offline` или `lost`) и начинает проверять.
- **Как проверяется:**
  - **Tidy Reel** — WebSocket фонового скрипта (`docs/extension/queues.md`, раздел 6), отдельных пробных запросов нет. Соединение открылось и ключ принят — `online`; оборвалось или не открылось — `offline` или `lost`;
  - **сервер синхронизации** — запросом `GET /api/v1/health` (`docs/sync_server/specification.md`, раздел 3).
- **Как часто проверяется, пока сервер не отвечает:**
  - **Tidy Reel** — раз в 5 секунд, пока фоновый скрипт не спит. Фоновый скрипт без открытого WebSocket Chrome усыпляет через 30 секунд, и его таймеры пропадают; тогда его будит `chrome.alarms` — раз в минуту, чаще Chrome не даёт;
  - **сервер синхронизации** — раз в 10 минут, тем же будильником, что спрашивает его о новых данных (`docs/extension/specification.md`, раздел 4); отдельного будильника нет;
  - **оба** — сразу, когда открывается страница расширения или popup, и при любой `ServerUnreachableError`.
- **Сервер ожил** — состояние `online`, и все, кто его читает, включают свои функции сами; перезагружать страницы и сайты не нужно. Тревога этого сервера снимается.
- В **настройках** состояние каждого сервера показывается вживую (`docs/extension/pages/settings.md`, раздел 1).

**Тревога при `lost`.** Сервер упал во время работы — пользователь должен пойти и посмотреть, почему, и перезапустить его.

- **Плашка «Нужно ваше решение»** (`docs/extension/queues.md`, раздел 4) с новыми случаями: «Tidy Reel перестал отвечать — перезапустите его» и «Сервер синхронизации перестал отвечать». Плашка общая со случаями очередей, с кнопкой «Заглушить». Показывается там же, где плашка очередей: вверху страниц расширения, в popup и на сайтах только на страницах видео — лишние сайты не нагружаются.
- **Уведомление Windows со звуком** повторяется раз в `notify_every_minutes`, пока пользователь не нажмёт «Заглушить» или сервер не оживёт. Одинаково для обоих серверов.
- **Случай** — сервер и время, с которого он не отвечает. «Заглушить» глушит этот случай; сервер ожил и упал снова — новый случай, звучит снова.
- **Показывает расширение**, а не Tidy Reel: упавший сервис о своём падении сообщить не может. Уведомление — `chrome.notifications`, повтор — будильник `chrome.alarms`.
- **`notify_every_minutes` хранится в Tidy Reel** (`docs/extension/pages/settings.md`, раздел 5). Расширение запоминает последнее полученное значение в `chrome.storage.local`; пока его не получало — 1 минута.

**Что происходит, когда Tidy Reel не отвечает** (`offline` или `lost`). Функции не прячутся, а становятся недоступными с подсказкой «Tidy Reel не отвечает»:

- «Скачать» в popup, галочка «Архив» в поиске, пресеты;
- кнопки на страницах очередей, «Подписки» и «Корзина»; последний полученный снимок остаётся на экране приглушённым, с полосой «Tidy Reel не запущен». Свои соединения эти страницы, пока Tidy Reel не отвечает, не открывают, а ждут `online` (`docs/extension/queues.md`, раздел 6);
- **плашка «Скачать» на сайтах исчезает полностью**: content script убирает её со страницы, не шлёт запросов и не следит за страницей, чтобы не нагружать сайт. Сервис снова `online` — content script снова проверяет страницу и показывает плашку, но только на видимой вкладке; скрытая проверит, когда её откроют (`docs/extension/pages/site_page.md`, раздел 3);
- учёт просмотров не останавливается: наблюдения копятся и уходят, когда сервис снова доступен (`docs/extension/specification.md`, раздел 3).

### 2.6.2. Скрытые вкладки

Решено 2026-10-16. Скрытая вкладка ничего не перерисовывает: так расширение бережёт ресурсы браузера. Видима вкладка, выбранная в своём окне, даже если окно не в фокусе (`document.visibilityState`).

- **Касается всего, где расширение рисует интерфейс:** страниц расширения и плашек на сайтах (плашка «Скачать», плашка «Уже сохранено»).
- **Хуки, подписанные на данные** (`useServerStatus`, `useAttention`, подписки на базу через `liveQuery`, снимки сервиса): пока вкладка скрыта, хук получает событие, но только запоминает последнее значение и не меняет состояние React — перерисовки нет. Вкладку открыли — хук применяет последнее значение одной перерисовкой. Это один общий помощник в `shared`, а не своя логика в каждой странице.
- **Content script** на скрытой вкладке сайта так же ничего не перерисовывает и применяет последнее состояние, когда вкладку открывают.
- Страницы очередей вдобавок отписываются от снимков сервиса, пока скрыты (`docs/extension/queues.md`, раздел 6).

### 2.6.3. Несохранённые изменения

Решено 2026-10-16. Изменение, которое пользователь сделал на странице, не должно пропасть молча, если он закрыл вкладку раньше, чем оно сохранилось.

- **Касается всех страниц расширения, где что-то редактируется:** настройки, переименование, пресеты, форма «Скачать» и подобное. Куда сохраняется — `chrome.storage`, Dexie или Tidy Reel — неважно.
- **«Идёт сохранение» начинается с первого изменения**: с первой буквы в поле, с щелчка по галочке. Время, пока поле ждёт паузы в наборе перед записью, тоже считается сохранением. Заканчивается, когда хранилище подтвердило запись.
- **Спиннер** — маленький, в шапке страницы справа, с подписью «Сохраняется…». Виден, пока хоть одно изменение не сохранено. После сохранения пропадает через секунду, без отдельной пометки «Сохранено».
- **Предупреждение при закрытии.** Пока идёт сохранение, страница включает `beforeunload`, и Chrome при закрытии вкладки или переходе спрашивает своё стандартное «Покинуть сайт?». Свой текст в этом окне Chrome не показывает; пояснение — подпись у спиннера. «Покинуть» — несохранённое пропадает; «Отмена» — пользователь ждёт, пока спиннер пропадёт. Сохранение закончилось — обработчик снимается, вкладка закрывается без вопроса.
- **Сохранение не удалось** (например, Tidy Reel не отвечает) — спиннер сменяется красной пометкой «Не сохранено» с кнопкой «Повторить». Предупреждение при закрытии остаётся, пока изменение не сохранится или пользователь не уйдёт сам.
- **Один общий помощник в `shared` — `useSavingGuard`**: страница отмечает начало и конец каждого сохранения, а спиннер, пометка и `beforeunload` — его забота.

### 2.7. Учёт просмотров на странице

- **Не в манифесте, а регистрируется из фонового скрипта** (решено 2026-10-16) через `scripting.registerContentScripts`: все сайты, во всех рамках (`all_frames`, `match_about_blank`). Регистрация есть, только если стоит галочка «Учёт просмотров» (`docs/extension/pages/settings.md`, раздел 6) и профиль подключён к Tidy Reel. Tidy Reel просто не отвечает (`offline`, `lost`) — регистрация остаётся, наблюдения копятся. Галочку сняли или профиль отключили — `unregisterContentScripts`, и в новые страницы ничего не внедряется. Регистрацию Chrome помнит сам, в том числе после перезапуска; фоновый скрипт при запуске только сверяет её с настройкой.
- **Уже внедрённый скрипт** из страницы не выгрузить: он слушает настройку и при выключении сразу снимает все свои обработчики и больше ничего не отправляет. Галочку поставили — учёт начинается на новых страницах и после обновления открытых.
- Скрипт на сайтах — во всех рамках. События плеера (`play`, `pause`, `seeking`, `timeupdate` и др.) не всплывают, поэтому слушаются на `document` в фазе перехвата.
- Фоновая вкладка определяется по `document.visibilityState`.
- Видео внутри закрытого Shadow DOM обычный скрипт не видит; если такие сайты встретятся — отдельный скрипт в контексте страницы.

### 2.8. Установка без магазина

Расширение не публикуется в Chrome Web Store (там нужен платный аккаунт разработчика): оно ставится распакованным в режиме разработчика.

- **Постоянный ID** задаётся ключом в манифесте (`key`). Он нужен для входа через Google и для проверки отправителя в локальном сервисе.
- **Обновление** — вручную: собрать новую версию и нажать «Обновить» на странице расширений в каждом профиле.
- Chrome может иногда напоминать, что включён режим разработчика.
