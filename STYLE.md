# Style guide

Правила кода. Всё, что проверяет форматтер или линтер, здесь не повторяется. Правила действуют для нового и изменяемого кода; старый код приводится к ним отдельными пунктами `docs/plan.md`.

## Принципы

- Код выглядит как окружающий: те же имена, плотность комментариев и приёмы.
- Читаемость важнее краткости. Простое решение лучше хитрого.
- Одна идея живёт в одном месте: похожую функциональность разных страниц и частей программы выносим в общий модуль или компонент, а не пишем дважды, чтобы правка в одном месте применялась везде.
- Единый стиль между страницами. Если одна страница проработана заметно подробнее других (структура, правила интерфейса, фильтры, иконки, кнопки, параметры в адресе), при работе над менее проработанной предлагай перенести туда те же удачные решения и сразу называй общий код, который для этого стоит выделить. Предлагай, а не делай молча; если решение странице не подходит, не тащи его и объясни почему. Без фанатизма и копирования «под копирку».
- Документация в `docs/` — источник правды. Если код с ней расходится, не выбирай сторону молча: покажи пользователю предупреждение с конкретным местом и предложи выбор: **(а)** обновить документацию под код в этом месте или **(б)** привести этот участок кода в соответствие документации. Пока пользователь не выбрал, не правь ни то, ни другое.

## Именование

- Имя говорит, что это такое, а не как устроено: `unfinishedDownloads`, а не `list2`.
- Без сокращений, кроме общепринятых (`db`, `id`, `url`, `sha1`).
- Функция называется глаголом (`findStale`, `getSettings`), значение и тип — существительным.
- Булево читается как утверждение: `isStale`, `hasTabs`.
- Функции и переменные `camelCase`, типы и компоненты `PascalCase`, константы `UPPER_SNAKE_CASE` (`RUN_DAYS_KEY`), файлы `kebab-case` (`find-stale.ts`).
- Тип называет роль: `SavedItem`, `StaleTarget`, а не `Data` и `Item2`.

## Структура

- Один модуль — одна тема. Над публичной функцией блок документации: что делает и на какой раздел `docs/` опирается.
- Слои FSD не смешиваем: `shared` ← `entities` ← `features` ← `widgets` ← `pages` ← `app`; слой знает только нижние. Фича не импортирует другую фичу: нужное ей передают параметром (см. `runAutoClose(save)`).
- Логика отдельно от интерфейса: расчёты в `model/`, компоненты только показывают и вызывают.
- Зависимости (браузер, база, часы) передаём параметром или берём из `shared`, чтобы подменить в тестах.
- Ориентир: функция помещается на экран, строка не длиннее 120 символов.

### Порядок в файле

Файл читается сверху вниз, как рассказ: сначала главное, потом детали. Функция, которая вызывает другие, стоит выше тех, кого вызывает, а её вспомогательные функции расположены сразу под ней, рядом с местом вызова. Не собирай все публичные функции наверху, а все помощники одной кучей внизу: у каждой «главной» функции свои помощники рядом. Константы и типы остаются в начале файла.

### Публичный интерфейс модуля

У каждого модуля (слайса, папки) есть файл входа `index.ts` (в Python это `__init__.py`). Он не пустой: в нём перечислено всё, что модуль отдаёт другим модулям, и только это (`export { runAutoClose } from './model/auto-close'`). Остальные модули импортируют из модуля целиком (`from '@/features/auto-close'`), а не из его файлов (`'@/features/auto-close/model/find-stale'`). Вспомогательные функции в этот список не попадают. Для слайсов FSD это и так требование Steiger.

- Тесты того же модуля могут импортировать из файла напрямую: это не другой модуль.
- Исключение: папка без собственных функций, только с подпакетами, может иметь пустой файл входа.
- Исключение: у слоя `app` по входу на каждую точку входа WXT (`@/app/background`, `@/app/offscreen`). Фоновый скрипт и служебная страница не должны тянуть через общий `index.ts` роутер, React и страницы: в фоновом скрипте нет DOM.

## Комментарии

- **Только на английском:** комментарии и docstring, без исключений.
- Комментируем «почему», а не «что»: код сам говорит, что он делает.
- Каждая публичная функция получает короткий docstring: что возвращает, одной строкой.
- Если за решением стоит правило, ссылка на него в docstring (`DUP-4`, `indexing.md, section 3`).
- Закомментированный код и `TODO` без задачи не оставляем.

## Тексты для пользователя

К ним относятся тексты интерфейса и тексты ошибок, которые видит пользователь.

- Пока локализации нет, они пишутся по-русски прямо в коде. Это не комментарии, правило про английский на них не распространяется.
- Когда появится локализация, все пользовательские строки (русский и другие языки, кроме английского) выносятся в файлы локализации. В коде остаётся только английский.
- Поэтому не склеивай фразы из кусков и не вставляй в текст логику: строка должна быть целой, с подстановками, чтобы её можно было вынести.

## Ошибки и данные

- Ожидаемые ошибки — свои классы (наследники `Error` с понятным именем), а не строки и не голый `Error`.
- Не глотаем ошибки молча: обрабатываем и говорим об этом либо пробрасываем.
- Широкий `catch` только на границе (обработчик сообщения, фоновая задача) и с записью в лог.
- Данные проверяем на входе (ответ сервиса, хранилище, ввод пользователя); внутри кода доверяем типам и не пишем `any`.
- Данные пользователя не теряем: перед необратимым действием подтверждение, запись в базу одной транзакцией.
- Время храним числом (миллисекунды), а не строкой; адреса разбираем через `URL`, а не регулярными выражениями.

## Тесты

- Тест лежит рядом с модулем (`find-stale.test.ts`), имя описывает поведение: `describe('pageKind', …)` и `it('treats a hash-only change as the same page', …)`.
- Один тест — одно поведение; несколько случаев одной проверки — `it.each`.
- Тесты не зависят от внешнего мира (браузер, сеть, сервис): подменяем зависимости, время передаём параметром.
- Исправляя ошибку, сначала пишем тест, который её ловит.
- Падающий тест не отключаем: чиним или удаляем с объяснением.

## Чего избегаем

- Русских комментариев и блоков документации.
- Дублирования вместо общего кода.
- Скрытых побочных эффектов: функция либо считает, либо меняет, не то и другое сразу.
- Бизнес-логики в обработчиках запросов и в интерфейсе.
- Магических чисел: константа с именем и комментарием, откуда она.
- Посторонних правок «заодно» в коммите чужой задачи.
